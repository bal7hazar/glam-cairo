# AP - `glam-cairo`: port Sum/Product, the slice APIs and `map` (92 glam-rs items now "dropped")

Repository **`bal7hazar/glam-cairo`** (this one). Read `AGENTS.md` (section "Before every push"), `docs/DESIGN.md`,
`tools/codegen/README.md` and the generators (`fvec.py`, `fmat.py`, `intvec.py` and their `*_tests.py`, `*_bench.py`),
`scripts/api_parity.py` (its `rule(...)` table) and `docs/API_PARITY.md`.

## Why

The programme now covers the Cairo primitives' API. `docs/API_PARITY.md` lists 92 glam-rs 0.33.8 items as "dropped" that
Cairo 2.20 can express. The project manager approved porting them, with conditions below; every other dropped family
stays dropped, with its reason.

## Scope, in this order

**A. `Sum` / `Product` (50 items).** Cairo 2.20's `core::iter::Sum<A>` and `core::iter::Product<A>` (in
`core/src/iter/traits/accum.cairo`) exist. Implement them for exactly the types whose glam-rs items the table lists as
dropped with "Iterator Sum/Product traits are deliberately omitted" (vectors, matrices, quaternion: read the table, do not
guess). Each folds **in iteration order, left to right**, starting from the type's `ZERO` (Sum) or `IDENTITY`/`ONE`
(Product), with the type's own `+` / `*`. That order is the determinism contract: write it in each doc comment.
Products of matrices and quaternions are not commutative: test the order. Overflow panics are those of `+` / `*`.

**B. Slice APIs (33 items).** `from_slice`, `write_to_slice`, `from_cols_slice`, `write_cols_to_slice`,
`from_rows_slice` become, in Cairo terms, `from_span(span: Span<T>) -> Self` (and `from_cols_span`, `from_rows_span`)
and `write_to(self, ref out: Array<T>)` (and `write_cols_to`). Lengths: glam-rs reads the first N elements and panics if
the slice is shorter. Choose and document one rule: either "exactly N" or "at least N, the first N are read" (the
second mirrors glam-rs), and a short span panics with a clear message, `'<Type>: span too short'` (or the crate's
existing message convention: check how other constructors panic). Test: N-1 panics, N works, N+1 per your rule. In the
parity table these items become **renamed**, with the Cairo name as the replacement.

**C. `map` (9 items), probe first.** `map` with a closure through `core::ops::Fn` (`fn map<F, +Fn<F, (T,)>[Output: T],
+Drop<F>>(self, f: F) -> Self`, or the form Cairo 2.20 accepts). Before writing all nine: implement one (`Vec3::map`),
measure with `scripts/consumer_cost.py` / `scripts/packages_table.py` (under the shared heavy-build lock) and count lines.
**If `map` would cost more than about 2 % of glam_core's lines in total, or adds a measurable marginal compile time, drop
C**: revert the probe, keep the items dropped with the reason updated ("measured: <figures>"), and say so in the report.
Otherwise implement all nine.

## Rules

- **Existing results unchanged**: every existing test, golden and API parity entry passes; `gas/*.snap` rows of
  existing functions do not move. New rows for the new functions are added.
- **Through the generators**: generated files (first line `// GENERATED by tools/codegen/...`) change only through
  their generator; hand-written files (check each) by hand.
- **Package size**: run the size gate (`scripts/consumer_cost.py`, `scripts/packages_table.py`, the same commands CI
  runs, under the heavy-build lock) and report every package's lines, marginal time and memory before and after. **If
  any package's margin falls under 10 %, stop and report**: do not push past the gate.
- **Parity table**: regenerate `docs/API_PARITY.md` (`scripts/api_parity.py --refresh` needs a glam-rs checkout; the
  committed inventory lets `--check` run without one: update the rules in `api_parity.py` so the ported items read
  ported or renamed). The declined families keep their reasons, word for word.
- Tests in each module's `#[cfg(test)] mod tests` where the repository's convention puts them, or in the generated test
  files; property tests within the existing fuzz budget.

`tools/codegen/**`, the files they generate (`packages/glam_core/src/*`, `packages/glam_int/src/*`,

## Done

Small conventional commits (`feat(api): ...`), push through the pre-push hook (never `--no-verify`), pull request with:
the item counts per group (A, B, C, and C's probe figures), the package-size table before/after, and the new parity
percentages per type. CI green, report with `Ready to merge at <sha>`. Batch all fixes of one review into one push.
Never merge unless prompted with a `Merge the PR` line. Never launch a review or any agent. Run everything in the
foreground.
